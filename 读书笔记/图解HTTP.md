### 1.1   使用HTTP协议访问Web

根据Web浏览器地址栏中指定的URL，Web浏览器从Web服务器端获取文件资源（resource）等信息，从而显示出Web页面，像这种通过发送请求获取服务器资源的Web浏览器等，可称为客户端（client）

Web使用一种名为HTTP（Hyper Transfer Protocol，超文本传输协议）的协议作为规范，完成从客户端到服务器端的一系列运作流程

**Web是建立在HTTP协议上通信的**

### 1.3   网络基础 TCP/IP

通常使用的网络（包括互联网）是在TCP/IP协议族的基础上运作的，HTTP属于它内部的一个子集

#### 1.3.1   TCP/IP协议族

计算机与网络设备要相互通信，双方就必须要基于相同的方法

比如，如何探测到通信目标，由哪一边发起通信，使用哪种语言进行通信，怎样结束通信等规则都需要事先确定，不同硬件，操作系统之间的通信，所有的一切都需要一种规则，我们就把这种规则称为**协议**（protocol）

> TCP/IP协议族里包含的协议（先做大概了解）
>
> ICMP（Internet Control Message Protocol，互联网控制报文协议）是 TCP/IP 协议族中的网络层协议，主要用于传递网络错误信息和诊断网络连通性
>
> IEEE 802.3 是由 IEEE（电气与电子工程师协会）制定的以太网（Ethernet）标准系列，主要规定有线局域网中 MAC 层和物理层的相关技术规范
>
> FDDI（Fiber Distributed Data Interface，光纤分布式数据接口） 是一种基于光纤传输的局域网技术，主要用于早期对高带宽、高可靠性要求较高的网络
>
> IP（Internet Protocol，互联网协议） 是 TCP/IP 协议族的核心协议，工作在网络层，主要负责为数据包提供逻辑寻址和跨网络转发机制，使数据能够从源主机传输到目标主机
>
> TCP（Transmission Control Protocol，传输控制协议） 是 TCP/IP 协议族中的传输层协议，主要负责在两台主机之间提供可靠、有序、面向连接的字节流传输
>
> UDP（User Datagram Protocol，用户数据报协议） 是 TCP/IP 协议族中的传输层协议，主要用于提供简单、低开销的数据报传输服务
>
> PPPoE（Point-to-Point Protocol over Ethernet，以太网上的点对点协议） 是一种将 PPP（点对点协议）封装在以太网中的网络技术，常用于家庭宽带接入，让用户通过以太网建立宽带连接并进行身份认证
>
> DNS（Domain Name System，域名系统） 是一种用于将域名转换为 IP 地址的分布式命名系统，也是互联网基础设施的重要组成部分
>
> FTP（File Transfer Protocol，文件传输协议） 是一种用于在客户端和服务器之间传输文件的应用层协议，支持文件上传、下载以及目录和文件管理等操作
>
> SNMP（Simple Network Management Protocol，简单网络管理协议） 是一种用于监控和管理网络设备的应用层协议，常用于管理路由器、交换机、服务器、防火墙、打印机等设备
>
> HTTP（Hypertext Transfer Protocol，超文本传输协议） 是一种应用层协议，用于客户端与服务器之间交换网页、图片、视频、API 数据等资源，是 Web 通信的基础

协议中存在各式各样的内容，从电缆的规格到IP地址的选定方法，寻找异地用户的方法，双方建立通信的顺序，Web页面显示需要处理的步骤等等

像这样把与互联网相关联的协议集合起来总称为TCP/IP

#### 1.3.2   TCP/IP的分层管理

TCP/IP协议族里最重要的一点就是**分层**

TCP/IP协议族按层次分别为以下四层，**应用层，传输层，网络层，数据链路层**

> 其实TCP/IP协议族有4层和5层两种不同的说法
>
> gpt叙述的4层是应用层，传输层，网络层，网络接口层
>
> 5层则是应用层，传输层，网络层，数据链路层，物理层
>
> 只是划分方式不同而已，仅做科普

把TCP/IP层次化是有好处的，比如如果互联网只是由一个协议统筹，当某个地方需要变化时，就必须把所有部分替换掉，而分层设计过后，只需要把对应的层替换掉

各层之间接口部分规划好之后，每个层次内部的设计就可以自由改动

值得一提的是，层次化之后，设计变得相对简单了，处于应用层的应用可以只考虑分派给自己的任务，而不需要弄清楚对方在地球上的哪个位置，对方传输路线是怎么样的，能不能确保传输送达等问题

TCP/IP协议族各层的作用如下

- 应用层

决定向用户提供应用服务时通信的活动

> 它定义应用进程之间交换数据的协议规则，包括消息格式、请求与响应机制、数据含义以及应用层交互流程，使不同主机上的应用程序能够按照统一规则进行通信

TCP/IP协议族内预存了各类通用的应用服务，比如FTP和DNS，HTTP也处在此层

- 传输层

传输层对上层应用层，提供处于网络连接中两台计算机之间的数据传输

> 传输层是 TCP/IP 协议体系中负责为不同主机上的应用进程提供端到端数据传输服务的一层。它的核心任务是利用端口号识别通信进程，并根据所使用的协议提供不同的数据传输服务

在传输层有两个性质不同的协议：TCP和UDP

- 网络层

网络层用来处理在网络上流动的数据包，数据包是网络传输的最小数据单位，该层规定了通过怎样的传输路径到达对方计算机，并把数据包传给对方

与对方计算机之间通过多台计算机或网络设备进行传输时，网络层起的作用就是在众多选项内选择一条传输路线

- 数据链路层

用来处理连接网络的硬件部分，包括控制操作系统和硬件的设备驱动，NIC（Network Interface Card，网络适配器，即网卡），光纤等物理可见部分（还包括连接器等一切传输媒介）

硬件上的范畴都在链路层的作用范围内

#### 1.3.3   TCP/IP通信传输流

利用TCP/IP协议族进行网络通信时，会通过分层顺序与对方通信，发送端从应用层往下走，接收端向应用层往上走，用HTTP举例来说明

1. 作为发送端的客户端在应用层（HTTP协议）发送一个想看某Web页面的HTTP请求
2. 为了传输方便，在传输层（TCP协议）把从应用层处收到的数据（HTTP请求报文）进行分割，并在各个报文打上标记序号和端口号后转发到网络层
3. 在网络层（IP协议），增加作为通信目的地的MAC地址后转发给数据链路层
4. 接收端的服务器在数据链路层收到数据，按顺序向上发送一直到应用层

发送端在层与层之间传输数据时，每经过一层就必定会被打上该层所属的首部信息，反之，接收端在层与层的传输数据时，每经过一层就消除对应的首部

这种把数据信息包装起来的做法叫封装（encapsulate）

> 发送端的流程就像是
>
> HTTP报文 ——> TCP报文 ——> IP数据包 ——> 网络架构
>
> 最终在数据链路层形成一个
>
> 由以太网首部 + IP首部 + TCP首部包装起来的HTTP数据

### 1.4   与HTTP关系密切的协议：IP，TCP，DNS

#### 1.4.1   负责传输的IP协议

IP协议位于网络层，作用是把各种数据包传送给对方

确保传送到对方，则需满足各种条件，其中最重要的两个就是IP地址，MAC地址

IP地址指明了节点被分配到的地址，MAC地址指网卡所属的固定地址，IP地址可以和MAC地址进行配对，IP地址可变换，MAC地址基本上不会改变

> MAC 地址的全称是 Media Access Control Address，中文通常称为媒体访问控制地址，MAC 地址通常在网卡生产时就被分配好了，存储在网卡相关的硬件或固件中，用来标识网络接口。 但要注意，它并不是绝对不能改变的，**是可以被软件或系统配置修改的**

在网络里，通信的双方位于同一局域网的情况很少，一般都是经过多台计算机和网络设备中转才能连接到对方，在进行中转时，会利用下一站中转设备的MAC地址来搜索下一个中转目标，此时会用到**ARP协议**，是一种用来解析地址的协议，根据通信方的IP地址就可以反查出对应的MAC地址

**没有人可以全面掌握互联网中的传输情况**

#### 1.4.2   确保可靠性的TCP协议

TCP位于传输层，提供可靠的字节流服务

所谓的字节流服务（Byte Stream Service）是指，为了方便传输，将大块头数据分割成以报文段（segment）为单位的数据包进行管理，可靠的传输服务则是指，能把数据准确可靠地传给对方

一句话，TCP为了更容易传输大块头数据才将其分割，还能确认数据最终是否传到对方手上

为了准确无误地将数据送到目标处，TCP协议采用了三次握手（three-way handshaking）策略，握手过程中使用了TCP的标志（flag）—— SYN（synchronize）和ACK（acknowledgement）

1. 发送端首先发送一个带SYN标志的数据包给对方
2. 接收端收到后，回传一个带有SYN/ACK标志的数据包
3. 发送端再回传一个ACK标志的数据包，代表握手结束

如果整个过程中某个阶段发生中断，TCP协议会以相同的顺序再次发送相同的数据包

#### 1.4.2   负责域名解析的DNS服务

DNS服务是和HTTP协议一样位于应用层的协议，它提供域名到IP地址之间的解析服务

计算机既可以被赋予IP地址，也可以被赋予主机名和域名，比如www.hacker.jp

> 用户通常使用主机名或域名来访问对方的计算机，而不是直接通过IP地址，因为除非闲的蛋疼或者对方的IP地址简单得像1 + 1 = 2这种情况，没人想去记一串八竿子打不着的数字，说实话我电话号码都懒的记
>
> 但计算机不擅长处理一段有规律的英文组合，它更擅长直接处理一大串莫名其妙的数字，为解决此情况，DNS服务诞生了，可以通过DNS服务从域名找到对应的IP地址，或者反过来从IP地址找到对应的域名

#### 1.4.3   各种协议与HTTP协议的关系

举例说明IP协议，DNS服务，TCP协议在使用HTTP协议的通信过程中各自发挥了哪些作用

1. 我闲来无事想访问一下樱花动漫网页
2. 客户端向DNS发请求，告诉我樱花动漫首页的IP地址吧
3. DNS返回樱花动漫首页对应的IP地址
4. HTTP协议开始干活，它的职责是生成针对目标Web服务器的HTTP请求报文 ” 请给我樱花动漫首页的资源啊 “
5. TCP协议开始干活，它的职责是为了方便通信，把HTTP请求报文分割成报文段（按序号分割），把每个报文段可靠的传给对方（三次握手）
6. IP协议开始干活，它的职责是搜索对方的地址，一边中转一边传送（在数量不明的路由器等网络设备里中转）
7. TCP协议又开始干活了，这一次它负责把接收到的报文段按序号以原来的顺序重组为请求报文
8. 到达目标服务器，HTTP协议又开始干活了，对请求进行处理，原来你想要这台计算机上樱花动漫的资源啊

### 1.5 URI 和 URL

#### 1.5.1 URI（统一资源标识符）

URI 是 Uniform Resource Identifier 的缩写，中文称为统一资源标识符。

URI 是一种用于标识资源的统一标识机制。它通过规定通用语法，使不同类型的资源能够按照统一的方式进行标识。

URI 由三个英文单词组成：

- **Uniform（统一）**

  提供统一的标识语法，使不同类型的资源标识符能够在相同的上下文中使用，同时允许引入新的标识方案，而不影响已有方案。

- **Resource（资源）**

  资源是指任何可以被标识的对象，其范围非常广泛。

  例如：
  - 文档、网页、图像。
  - 网络服务，例如天气预报服务。
  - 现实中的人、公司、书籍。
  - 数学中的抽象概念。

- **Identifier（标识符）**

  用于区分和标识特定资源的信息，使其能够与其他资源区分开来。

**综上所述：URI 是用于统一标识资源的字符串。它的核心作用是标识资源，不意味着该资源一定能够被访问或获取。**

#### 1.5.2 URL 与 URI 的关系

URL 是 Uniform Resource Locator 的缩写，中文称为统一资源定位符。

**URL 是 URI 的子集。**

URI 主要负责标识资源，而 URL 除了标识资源，还提供用于定位或访问资源的信息。

例如：

- URL：`https://www.example.com/index.html`

  通过 HTTPS 方案、域名和路径等信息定位资源。

- URN：`urn:isbn:978...`

  使用统一资源名称方案标识一本书，不直接提供 HTTP 服务器地址。

URI 可以分为以下几种理解方式：

- Name：资源名称。
- Locator：资源定位信息。
- Name + Locator：同时具有名称和定位功能。

#### 1.5.3 URI Scheme（URI 方案）

Scheme 是 URI 最前面的方案名称，用于确定 URI 应当按照什么规则进行解释和处理。

常见的 URI Schemes：

| Scheme | 用途                    |
| ------ | ----------------------- |
| http   | HTTP 资源标识方案       |
| https  | HTTPS 资源标识方案      |
| ftp    | FTP 资源标识方案        |
| file   | 文件资源标识方案        |
| mailto | 电子邮件地址标识方案    |
| urn    | 统一资源名称方案        |
| data   | 将数据直接包含在 URI 中 |

URI Scheme 的注册信息由 IANA（Internet Assigned Numbers Authority，互联网号码分配局）维护。

官方注册表：
https://www.iana.org/assignments/uri-schemes

#### 1.5.4 URL 的基本结构

以以下 URL 为例：

`http://user:pass@www.example.jp:80/dir/index.htm?uid=1#ch1`

常见 HTTP URL 的结构可以表示为：

`scheme://[userinfo@]host[:port]/path[?query][#fragment]`

其中，方括号表示该部分可选，并非 URL 中需要输入的实际字符。

各组成部分：

**1. Scheme（方案）**

`http`

表示 URI 所采用的标识方案。在该例中使用 HTTP。

`:` 是 Scheme 与后续部分之间的分隔符，`//` 表示后面开始 Authority（授权机构/权限信息）部分。

**2. Userinfo（用户信息）**

`user:pass`

用于表示用户名以及可选的授权相关信息。

- user：用户名。
- pass：示例中的密码字段。
- @：分隔 Userinfo 与 Host。

注意：在 URI 中使用 `user:password` 的形式已经不推荐，因为可能造成敏感凭据泄露。实际应用中不要将密码直接写进 URL。

**3. Host（主机）**

`www.example.jp`

表示 URI 中的主机部分。

Host 可以采用：
- 域名，例如` www.example.com`
- IPv4 地址，例如 192.168.1.1。
- IPv6 地址，例如 [2001:db8::1]。

**4. Port（端口）**

`80`

表示访问目标使用的端口号。

端口用于区分同一主机上不同的网络服务。

该部分是可选的。省略时通常根据 URI Scheme 使用对应的默认端口。

常见默认端口：

- HTTP：80
- HTTPS：443

**5. Path（路径）**

`/dir/index.htm`

用于描述资源在 URI 标识体系中的层次路径。

其中：
- 第一个 `/` 表示路径从当前 Authority 的根路径开始。
- `dir` 表示路径中的一个层级。
- `index.htm` 表示最后一个路径段。

注意：Path 不一定对应服务器上的真实文件，也可能是 Web 应用程序中的路由或接口路径。

**6. Query（查询组件）**

`?uid=1`

`?` 表示 Query 组件的开始。

`uid=1` 是查询数据，在常见 Web 应用中通常表示一个参数及其对应的值。

例如：

`https://example.com/search?keyword=python&page=2`

- keyword=python：搜索关键词。
- page=2：页码。

Query 可以包含多个参数，常见形式使用 `&` 进行分隔。

Query 的具体含义和处理方式由对应的服务或应用程序决定。

**7. Fragment（片段标识符）**

`#ch1`

`#` 表示 Fragment 组件的开始。

ch1 是片段标识符，用于进一步定位主要资源中的某个部分或视图。

例如，在 HTML 页面中：

`https://example.com/article#chapter1`

通常可以定位到页面中 id 为 chapter1 的元素。

重要：

对于 HTTP/HTTPS 请求，Fragment 不会被发送到服务器，而是由客户端处理。

#### 1.5.5 Query 与 Fragment 的区别

以以下 URL 为例：

`https://example.com/article?id=100#chapter1`

- `?id=100`：Query，属于查询组件，通常会随 HTTP 请求发送给服务器。
- `#chapter1`：Fragment，属于片段标识符，不会被包含在 HTTP 请求目标中。

可以简单记忆：

Query：向服务器提供查询数据。

Fragment：在客户端进一步定位资源中的内容。

#### 1.5.6 RFC

RFC 是 Request for Comments 的缩写，通常译为征求意见系列文档。

RFC 是互联网技术文档系列，内容包括：

- Internet Standards（互联网标准）。
- Technical Specifications（技术规范）。
- Protocols（协议）。
- Procedures（流程和方法）。
- Research and Informational Documents（研究和信息性文档）。

注意：并非所有 RFC 都是正式互联网标准。

URI 通用语法的重要标准：

RFC 3986：
Uniform Resource Identifier (URI): Generic Syntax

https://www.rfc-editor.org/rfc/rfc3986

## 第二章   简单的HTTP协议

### 2.1   HTTP协议用于客户端和服务器端之间的通信

请求访问文本或图像等资源的一端称之为**客户端**

提供资源响应的一端称之为**服务器端**

来看具体实例：

```
#发送请求
GET /index.htm HTTP/1.1
Host: hacker.jp

#发送响应
HTTP/1.1 200 OK
Date: Tue, 10 Jul 2012 06:50:15 GMT
Content-Length: 362
Content-Type: text/html
<html>
...
```

请求报文：

起始行GET表示**请求访问服务器的类型，称之为方法**

随后的字符串/index.htm指明了**访问的资源对象**，也叫**请求URI**

最后的HTTP/1.1是HTTP的版本号，用来提示客户端使用的HTTP协议功能

综合来看，这段请求的意思是：请求某台HTTP服务器上的/index.htm页面资源

**请求报文是由，请求方法，请求URI，HTTP协议版本，可选的请求首部字段，内容实体组成的**



返回报文：

起始行开头的HTTP/1.1表示服务器对应的HTTP版本

200 OK对应请求的处理结果的状态码和原因短语

下一行显示了创建响应的时间，是首部字段的一个属性



**HTTP是不保存状态的协议**

HTTP是一种无状态协议，自身不对请求和响应之间的通信状态进行保存，不做持久化处理

使用HTTP协议，每当有新的请求发送时，就会有对应的新的响应产生，协议本身不保留之前的一切请求或响应报文的信息，**这是为了更快地处理大量事务，确保协议的可伸缩性，特意把HTTP设计的这么简单**

但随着时代发展，无状态会导致业务处理变得棘手，比如用户网上购物，登录个人信息后跳转到该购物网站的其他页面，也应该要保持登录状态

所以，虽然HTTP/1.1是无状态协议，但为了保持状态功能，引入了**Cookie**技术



**HTTP协议使用URI定位互联网上的资源**

如果不是访问特定资源而是对整个服务器本身发起请求，用 * 代替请求URI

```
OPTIONS * HTTP/1.1
```

### 2.2   告知服务器意图的HTTP方法

#### GET：获取资源

**GET方法用来请求访问已经被URI识别的资源**

> 什么叫已经？
>
> 它真正想表达的是：**这个资源已经有一个 URI 可以用来标识它了**

**GET主要用来获取指定资源，也就是服务器在响应主体中返回的相应数据**

#### POST：传输实体主体

**POST方法用来传输实体的主体**

GET也能传输实体的主体，但一般不用

也就是说，**GET 的核心思想是「我要获取资源」**

**而POST 则是「我要向服务器提交数据，请服务器根据这些数据进行处理。」**

最常见的POST就是，注册账号提交用户名，密码

#### PUT：传输文件

要求在请求报文的主体里包含文件内容，然后保存到请求URI指定的位置

```
PUT /users/123 HTTP/1.1
Host: example.com

{
  "username": "John",
  "age": 23
}
```

**HTTP/1.1的PUT方法不带验证机制，任何人都可以上传文件，存在安全性问题，一般网站不会用**

**如果，配合web应用程序的验证机制，或架构设计采用REST标准的同类web网站，就可能开放这个方法**

> 在渗透测试中，如果发现目标网站开放了 PUT 方法，需要进一步检查是否存在未授权文件上传或资源覆盖等安全问题

在渗透测试中，我们经常会关注目标网站开放了哪些 HTTP 方法

```
curl -X OPTIONS https://example.com -i
```

服务器可能通过 `Allow` 响应头告诉客户端支持哪些方法：

```
HTTP/1.1 200 OK
Allow: GET, POST, PUT, DELETE
```

#### HEAD：获取报文首部

HEAD 可以理解为 GET 的一个特殊版本

两者最大的区别是：**HEAD 请求只获取服务器响应头，不获取响应主体（Response Body）**

在渗透测试中，安全测试人员有时会使用 HEAD 检查目标资源

```
curl -I https://example.com
```

#### DELETE：删除文件

与PUT一样，但作用相反，所以PUT的性质该有的，DELETE也有，不多赘述

#### OPTIONS：询问支持的方法

OPTIONS 方法用于查询服务器或指定资源支持的通信选项

```
OPTIONS * HTTP/1.1
Host: example.com
```

```
HTTP/1.1 200 OK
Allow: GET, POST, OPTIONS
```

> 补充知识点之**CORS 预检请求（Preflight Request）**
>
> 它是 HTTP OPTIONS 方法在 Web 开发和 Web 安全中一个非常重要的应用场景
>
> **CORS 预检请求，就是浏览器在正式发送某些跨域请求之前，先向服务器发送一个 OPTIONS 请求，询问服务器是否允许这次跨域操作。**
>
> **什么是跨域（Cross-Origin）**
>
> 假设你正在访问一个网站：
>
> ```
> https://www.example.com
> ```
>
> 这个网页中的 JavaScript 想要向另一个网站请求数据：
>
> ```
> https://api.example.com/users
> ```
>
> 虽然它们都属于 `example.com`，但两者的主机名不同，因此属于不同的源（Origin）
>
> 浏览器有一个安全机制，叫作**同源策略（Same-Origin Policy）**
>
> 一个源由三个部分组成：
>
> - 协议（Protocol）：HTTP、HTTPS。
> - 主机（Host）：域名或 IP 地址。
> - 端口（Port）：例如 80、443、8080。
>
> 这三个部分只要有一个不同，就属于不同的源
>
> CORS，全称 Cross-Origin Resource Sharing，中文叫**跨域资源共享**
>
> 它是一种基于 HTTP 响应头的机制，允许服务器声明哪些其他源可以访问它的资源
>
> 例如，服务器返回：
>
> ```
> Access-Control-Allow-Origin: https://www.example.com
> ```
>
> 意思是：
>
> 「我允许来自 `https://www.example.com` 这个源的浏览器网页访问我的资源。」
>
> 并不是所有跨域请求都需要预检。
>
> 浏览器会根据请求的方法、请求头和其他条件判断是否需要预检
>
> 例如：
>
> | 请求情况                                   | 通常是否需要预检 |
> | ------------------------------------------ | ---------------- |
> | GET 普通跨域请求                           | 不需要           |
> | POST 普通表单请求                          | 不需要           |
> | PUT 跨域请求                               | 需要             |
> | DELETE 跨域请求                            | 需要             |
> | 携带自定义请求头                           | 需要             |
> | POST 使用 `Content-Type: application/json` | 需要             |
>
> **这里所说的不需要预检，指符合 CORS 安全名单条件的请求，也就是所谓的简单请求**
>
> **为什么要有这个机制？**
>
> 因为浏览器需要在发送某些可能产生重要副作用的跨域请求之前，先确认服务器是否允许这种请求。
>
> **预检请求是如何工作的？**
>
> **1. 浏览器发送 OPTIONS 预检请求**
>
> ```
> OPTIONS /users/123 HTTP/1.1
> Host: api.example.com
> Origin: https://www.example.com
> Access-Control-Request-Method: PUT
> Access-Control-Request-Headers: content-type, authorization
> ```
>
> 这里有三个重要请求头：
>
> | 请求头                         | 含义                                   |
> | ------------------------------ | -------------------------------------- |
> | Origin                         | 告诉服务器请求来自哪个源               |
> | Access-Control-Request-Method  | 告诉服务器正式请求想使用什么 HTTP 方法 |
> | Access-Control-Request-Headers | 告诉服务器正式请求准备携带哪些请求头   |
>
> **2. 服务器返回预检响应**
>
> 如果服务器允许，可以返回：
>
> ```
> HTTP/1.1 204 No Content
> Access-Control-Allow-Origin: https://www.example.com
> Access-Control-Allow-Methods: GET, POST, PUT
> Access-Control-Allow-Headers: Content-Type, Authorization
> Access-Control-Max-Age: 3600
> ```
>
> 重点认识这几个响应头：
>
> | 响应头                       | 含义                           |
> | ---------------------------- | ------------------------------ |
> | Access-Control-Allow-Origin  | 允许哪个来源访问               |
> | Access-Control-Allow-Methods | 允许使用哪些 HTTP 方法         |
> | Access-Control-Allow-Headers | 允许携带哪些请求头             |
> | Access-Control-Max-Age       | 预检结果可以缓存多长时间（秒） |
>
> **3. 浏览器发送正式 PUT 请求**
>
> 预检通过后，浏览器才会继续发送正式请求：
>
> ```
> PUT /users/123 HTTP/1.1
> Host: api.example.com
> Origin: https://www.example.com
> Content-Type: application/json
>
> {
>   "username": "John"
> }
> ```
>
> 服务器接收到请求后，才会执行相应的业务处理。
>
> 如果预检失败，浏览器通常不会发送这次正式请求。
>
> **从网络安全角度看，应该注意什么？**
>
> **CORS 配置错误可能造成安全问题**
>
> 例如，服务器错误地允许不可信来源访问敏感数据，可能导致跨站读取敏感信息等安全风险

#### TRACE：追踪路径

TRACE 方法是让 Web 服务器端将之前的请求通信环回给客户端的方法

发送请求时，在 Max-Forwards 首部字段中填入数值，每经过一个服务器端就将该数字减 1，当数值刚好减到 0 时，就停止继续传输，最后接收到请求的服务器端则返回状态码 200 OK 的响应

客户端通过 TRACE 方法可以查询发送出去的请求是怎样被加工修改 / 篡改的。这是因为，请求想要连接到源目标服务器可能会通过代理中转，TRACE 方法就是用来确认连接过程中发生的一系列操作

但是，TRACE 方法本来就不怎么常用，再加上它容易引发 XST（Cross-Site Tracing，跨站追踪）攻击，通常就更不会用到了

> 现代 Web 应用通常有其他更灵活的调试方式，因此 TRACE 在日常开发中的使用并不普遍

#### CONNECT：要求用隧道协议连接代理

CONNECT 方法要求在与代理服务器通信时建立隧道，实现用隧道协议进行 TCP 通信

主要使用 SSL（Secure Sockets Layer，安全套接层）和 TLS（Transport Layer Security，传输层安全）协议把通信内容加密后经网络隧道传输

这里先理解两个概念：

- **代理服务器（Proxy）：** 充当客户端与目标服务器之间的中间人，负责转发通信。
- **隧道（Tunnel）：** 在客户端与目标服务器之间建立一条可以传输数据的逻辑通道。

你可以把它理解为：

客户端无法直接与目标服务器通信，于是先联系代理服务器，请代理服务器帮助建立一条通往目标服务器的通信通道

假设你想通过 HTTP 代理访问一个 HTTPS 网站：

```
https://www.example.com
```

代理服务器地址：

```
192.168.1.100:8080
```

通信过程如下：

**第一步：客户端向代理服务器发送 CONNECT 请求**

```
CONNECT www.example.com:443 HTTP/1.1
Host: www.example.com:443
```

**第二步：代理服务器建立隧道**

代理服务器收到请求后，会尝试连接

如果连接成功，代理服务器返回：

```
HTTP/1.1 200 Connection Established
```

**第三步：客户端通过隧道进行 HTTPS 通信**

隧道建立后，客户端开始进行 TLS 握手，随后通过建立的加密连接发送 HTTPS 请求和接收响应

这里有一个非常重要的知识点：

**CONNECT 建立隧道后，代理服务器通常只负责转发加密数据，并不直接读取 HTTPS 通信中的具体内容**

除非使用了 HTTPS 中间人解密等特殊技术

**CONNECT 有什么用途？**

主要有以下几个：

1. **HTTPS 代理：** 通过 HTTP 代理建立通往 HTTPS 服务器的隧道。
2. **代理通信：** 让客户端通过代理服务器访问指定目标。
3. **加密通信：** 隧道建立后，可以在其中进行 TLS 加密通信。

**从网络安全角度看 CONNECT**

例如：

**1. 未授权代理访问**

如果代理服务器允许任意用户使用 CONNECT，攻击者可能滥用它访问其他网络资源。

**2. 内网访问风险**

如果代理服务器能够访问内部网络，而又没有合理的访问控制，可能被滥用为访问内网服务的跳板。

**3. 端口访问限制**

代理服务器通常应该限制 CONNECT 可以连接的目标端口，例如只允许连接常见的 HTTPS 端口 443。

> 知识补充：
>
> **CONNECT 和 VPN 有什么共同点？**
>
> 你可以先这样理解：
>
> - **HTTP CONNECT：** 通过代理服务器建立一条通往目标服务器的通信隧道。
> - **VPN：** 在设备与 VPN 服务器或 VPN 网络之间建立一条虚拟专用网络通道。
>
> 它们都能让数据通过一个中间节点进行传输。
>
> **核心区别**
>
> | 对比项目 | HTTP CONNECT              | VPN                          |
> | -------- | ------------------------- | ---------------------------- |
> | 主要目的 | 建立代理隧道              | 建立虚拟专用网络             |
> | 工作范围 | 通常针对指定目标          | 通常覆盖一组网络流量         |
> | 所属技术 | HTTP 代理机制             | VPN 网络技术                 |
> | 是否加密 | CONNECT 本身不加密        | 通常使用加密隧道             |
> | 常见协议 | HTTP/1.1、HTTP/2 扩展机制 | IPsec、WireGuard、OpenVPN 等 |
>
> 特别注意：HTTP CONNECT 本身不提供加密，但如果通过它建立 HTTPS 隧道，隧道内的 TLS 通信通常是加密的。

### 2.3   持久连接

持久连接的特点是，只要任意一端没有明确提出断开连接，则保持 TCP 连接状态

持久连接（HTTP Persistent Connections，也称为 HTTP keep-alive 或HTTP connection reuse）

持久连接的好处在于减少了 TCP 连接的重复建立和断开所造成的额外开销，减轻了服务器端的负载。另外，减少开销的那部分时间，使HTTP 请求和响应能够更早地结束，这样 Web 页面的显示速度也就相应提高了

### 2.4   管线化

持久连接使得多数请求以管线化（pipelining）方式发送成为可能，这样就能够做到同时并行发送多个请求，而不需要一个接一个地等待响应了

管线化方式是：
连续发送多个请求 → 再依次接收响应

**为什么现在很少使用 HTTP/1.1 管线化？**

因为它有一个比较明显的问题：**队头阻塞（Head-of-Line Blocking，HOL Blocking）**

```
请求1：获取一个很大的文件
请求2：获取一张小图片
请求3：获取一份JSON数据
```

假设服务器处理完请求 1 需要 10 秒，而请求 2 和请求 3 只需要 1 秒

由于 HTTP/1.1 管线化要求按照请求顺序返回响应，即使请求 2 和请求 3 已经处理完成，也必须等待请求 1 的响应先返回

**HTTP/2 如何改进？**

HTTP/2 引入了一个重要机制：**多路复用（Multiplexing）**

它允许在同一个 TCP 连接上，同时交错传输多个请求和响应的数据帧

HTTP/2 解决了 HTTP/1.1 应用层管线化的队头阻塞问题。

不过要注意：**HTTP/2 底层通常仍使用 TCP**，TCP 层发生丢包时，仍可能造成多个数据流受到影响。

HTTP/3 则使用 QUIC 传输协议，进一步解决了这种 TCP 层面的队头阻塞问题。

> 到底怎么去理解多路复用？
>
> ```
> 客户端同时发出三个请求，请求A/请求B/请求C
>                   ⬇
>     服务器将响应拆成多个数据帧（Frame）
> 	A			B			C
> 	A1			B1			C1
> 	A2			B2			C2
> 	A3			B3			C3
> 				⬇
> 		在同一个连接中交错传输
> A1-->B1-->C1-->A2-->C2-->B2-->A3-->B3-->C3
> ```
>
> 这样一来：
>
> - A 的数据可以分批传输。
> - B 的数据不必等待 A 全部传完。
> - C 的数据也可以穿插进来。
> - 客户端收到数据后，根据数据帧所属的流（Stream）重新组装。
>
> **HTTP/2 是如何实现多路复用的 ?**
>
> 这里有2个重要概念：
>
> | 概念         | 含义                                              |
> | ------------ | ------------------------------------------------- |
> | Stream（流） | 一次独立的 HTTP 请求与响应交换所对应的逻辑通道    |
> | Frame（帧）  | HTTP/2 通信的最小协议单位，实际数据被拆分成帧传输 |

### 2.5   HTTP/3的QUIC协议

如果HTTP/2 的多个 Stream 共用一条 TCP 连接。如果 TCP 传输过程中某个数据段丢失，那么 TCP 必须先处理丢失的数据，才能按序向上层交付后续数据。
